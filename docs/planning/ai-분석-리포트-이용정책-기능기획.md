# AI 분석 리포트 이용 정책 기능 기획

- 작성일: 2026-08-03 / 상태: 확정
- 연관 문서: `docs/ai-analysis-feature-plan.md`(UI/UX 원안, 2026-06-09), `docs/planning/수익화-기능기획.md`(수익화 전체 기획, 2026-07-06, 확정)
- 성격: **부분 기획(정책 개정)**. AI 분석 리포트 기능 자체(화면 흐름, 상태머신, 데이터 구조)는 이미 구현·확정되어 있고, 이 문서는 그중 "이용 횟수·트라이얼" 정책만 오늘 논의로 갱신한다. 확정되면 `수익화-기능기획.md` §0.5 무료 맛보기 정책, §3 플랜·무료 정책, §4.1 재생성/무료사용자 조항을 이 문서 내용으로 교체한다.

## 0. 착수 배경

- 사용자가 AI 분석 리포트의 현재 UI/UX 흐름(랜딩 → 목록/종류 선택 → Q&A 선택 → 생성 요청 → FCM 알림 → 결과 확인, 종류는 향후 확장 예정)을 설명하며, 다음 세 가지를 새로 고민 중:
  1. 결제(IAP)를 아직 붙이지 않은 현재 상태에서 리포트 생성 횟수를 어떻게 제한할지
  2. 결제를 붙인 이후 최종적으로 트라이얼(7일)과 구독자 한도를 어떻게 설계할지
  3. 앱이 1년 주기로 질문을 순환 제공하는데, 분석 리포트의 데이터 소스(답변)도 1년 단위로 끊어야 하는지
- **이미 확정되어 재론하지 않는 것** (코드/문서로 확인됨):
  - 화면 흐름·라우트 구조·상태머신(`docs/ai-analysis-feature-plan.md` §3~5, 코드 `src/app/(tabs)/analysis/*`, `src/features/analysis/domain/analysisStatus.ts`)
  - 리포트 종류는 현재 2종(사고패턴/따뜻한 회고), 향후 확장 가능 (`수익화-기능기획.md` §4.1)
  - 분석 대상 답변 선택: 최소 10 ~ 최대 15개, 사용자 직접 선택 (`analysisTypes.ts` MIN/MAX_ANSWERS)
  - 완료 알림은 FCM, 폴링 미사용(`focusManager` 기반)
  - 리포트는 본인만 열람, 만료 후에도 생성 당시 접근 권한 유지
  - 구독 검증은 서버(RevenueCat webhook), 클라이언트는 서버 판정을 그대로 표시
  - **기존 수익화 문서와 충돌해 갱신 대상인 것 (사용자 확인 완료 — 오늘 내용으로 갱신)**: 무료 이용 횟수(구 "평생 1회"), 트라이얼 유무(구 "트라이얼 없음"), 구독자 월 한도(구 "월 10회")

## 진행 순서

아래 네 주제를 하나씩 확정한다. 한 주제가 끝나야 다음으로 넘어간다.

1. **결제 전(현재) 임시 이용 정책** — IAP 인프라가 없는 지금, 서버에서 어떻게 횟수를 제한할지
2. **결제 후 최종 정책** — 트라이얼(7일) + 구독자 한도의 구체 규칙
3. **1년 주기와 데이터 범위** — 분석 대상 답변을 연차로 제한할지
4. **결과 콘텐츠 포맷** — 리포트 결과를 마크다운으로 받을지 평문(구조화 JSON)으로 받을지
   - 현재 코드(`ResultContent.tsx`)는 서버가 구조화 JSON(`summary`+`sections[]` 또는 `letter` 문자열)을 준다고 가정하고 그대로 `Text`로 렌더링 — 마크다운 파서 없음. 아직 실서버 조회 계약이 없으므로 지금 확정하면 서버 계약에 반영 가능.

(진행 중 — 아래 섹션은 각 주제 확정 시 채워짐)

## 주제 1. 결제 전(현재) 임시 이용 정책 (확정)

- **한도**: 리포트 종류당 월 2회 (사고패턴 2회 + 따뜻한 회고 2회 = 사용자 기준 최대 월 4회). 종류 확장 시 종류 수만큼 자동으로 늘어남
- **리셋 기준**: 캘린더 월 1일 0시. 서버가 판정(`수익화-기능기획.md`의 "구독 검증은 서버에서" 원칙과 동일선상)
- **주의**: 이 한도는 "몇 번 생성 요청할 수 있는가"에 대한 카운터이며, 분석 대상 답변의 날짜 범위와는 무관하다. 답변 선택은 기존 정책대로 임의의 답변 10~15개를 자유롭게 고를 수 있어 캘린더 월 경계에 걸친 데이터(예: 7월 말~8월 초)도 문제없이 한 리포트에 포함 가능
- **유효기간**: 잠정 정책. **결제(IAP) 도입 시 아래 주제 2 정책으로 완전 대체**되며, 이 조항은 폐기된다
- **서버 영향**: `GET /api/v1/analyses/availability` 응답이 종류 무관 단일 게이트(`docs/ai-analysis-feature-plan.md` §6 제안 계약, 코드상 `AnalysisAvailability`)로 되어 있다면 **종류별 가용성**을 반환하도록 계약을 확장해야 한다 — API 계약 변경이므로 서버 협의 필요

## 주제 2. 결제 후 최종 정책 — 7일 트라이얼 + 구독 (확정)

- **트라이얼 방식**: 스토어 IAP 트라이얼(RevenueCat) — 결제수단 등록 필요, 7일 후 자동 결제 전환
- **트라이얼 시작 시점**: 사용자가 "구독하기"를 눌러 결제수단을 등록하는 시점부터 (앱 설치·가입과 무관, 페이월 진입 시 트리거)
- **트라이얼 중 한도**: 7일간 리포트 종류당 1회 (원 발화 그대로 — 현재 2종 기준 트라이얼 기간 중 최대 2회)
- **트라이얼 종료 후 미결제 시**: **완전 잠김** — 생성 0회. 트라이얼은 1회성 체험 혜택이며, 이후 미결제 사용자는 (주제 1의 "월 2회 무료"로 돌아가지 않고) 결제해야만 생성 가능
- **구독자 한도**: 리포트 종류당 월 2회 (최대 월 4회) — 주제 1과 동일한 종류별 독립 카운트 구조로 통일. 리셋 기준도 동일하게 캘린더 월 1일로 간주(별도 이견 없었음)
- **`수익화-기능기획.md` 대체 조항**: §0.5 "첫 월간 리포트 1회 전체 무료", §3 "무료 사용자 평생 통합 1회 / 트라이얼 없음", §4.1 "구독자 월 생성 한도 10회" → 위 내용으로 전면 교체
- **해지/만료 후 상태(확인 완료)**: 구독을 해지하거나 결제 실패로 만료된 사용자는 이미 트라이얼을 사용한 이력이 있으므로, 주제 1의 "월 2회 무료"로 되돌아가지 않고 **완전 잠김**(재구독해야 생성 가능) 상태가 된다
- **리셋 기준 통일(확인 완료)**: 구독자의 "월 2회" 리셋 기준도 주제 1과 동일하게 캘린더 월 1일 0시

## 주제 3. 1년 주기와 분석 데이터 범위 (확정)

- **분석 대상 답변은 현재 연차(사용자별 가입일 기준 1년 주기)로 제한**한다. 리포트 생성 시 선택 가능한 답변 후보는 진행 중인 연차의 답변만
- **연차 전환 직후 처리**: 새 연차 답변이 아직 10개 미만이면 기존 `LOCKED` 게이트를 그대로 적용(예외 로직 없음). 최대 약 9일간 분석 불가 구간이 생기되, 신규 사용자도 동일하게 겪는 기존 패턴이라 새로운 예외가 아님
- **채택 근거(사업성)**: "이번 해의 나를 분석한다"는 서사 일관성이 "1년마다 새로 시작"이라는 앱 정체성과 맞고, 리포트 히스토리를 "N년차" 단위로 구분해 보여주는 것 자체가 재구독 유인(매년 새 리포트를 받고 싶게)이 될 수 있음. 직전 연차로 부족분을 보완하는 예외는 구현 복잡도 대비 이득이 작아 채택하지 않음
- **구현 영향**: 리포트 생성 화면(Q&A 선택, `select.tsx`)의 답변 후보 조회가 "현재 연차"로 스코프되어야 함 — 서버 API가 연차 경계를 판정하거나(선호), 클라이언트가 연차 시작일을 계산해 필터링

## 주제 4. 결과 콘텐츠 포맷 (확정)

두 층위로 나눠 결정한다 — ① 응답 봉투 구조 ② 그 안 텍스트 필드 값의 문법 허용 범위.

- **① 봉투: 구조화 JSON 유지**. AI(서버)가 고정 스키마 필드(사고패턴: `summary` + `sections[{title, items[]}]`, 따뜻한 회고: `letter` 문자열)로 응답하고, 클라이언트는 현행 `ResultContent.tsx`처럼 각 필드를 앱 디자인시스템(Tamagui, 액센트 컬러, i18n)으로 네이티브 렌더링한다
- **② 필드 값: 순수 문자열, 마크다운 문법 없음**. `summary`/`letter`/`items[]` 각 원소는 일반 텍스트(줄바꿈이 필요하면 `\n`)이며 `**굵게**` 등 마크다운 강조 문법을 포함하지 않는다. 이유: 현행 `ResultContent.tsx`와 100% 일치해 파서가 전혀 불필요하고, AI가 마크다운 문법을 잘못 섞어 낼 위험도 없앰 — 강조가 필요한 구조(제목/리스트)는 이미 JSON 스키마(`sections`, `items`)가 담당하므로 필드 내부 인라인 강조까지는 불필요하다고 판단
- 마크다운 렌더링 라이브러리는 도입하지 않는다 (신규 의존성 없음)
- **서버 잔여 과제(참고, 이번 문서 범위 아님)**: AI 응답이 스키마를 벗어나거나 필드 값에 마크다운 문법이 섞여 나올 경우의 검증/새니타이즈 전략은 서버 구현 시 별도 결정 필요

## 오픈 이슈

1. **API 계약 변경 필요**: `availability` 응답을 종류별 구조로 확장하는 작업은 서버와 별도 협의 필요 (이 문서는 정책만 확정, 스키마 상세는 서버 몫)
2. **AI 응답 검증 전략**: 구조화 JSON 스키마를 AI가 벗어나거나 필드에 마크다운이 섞여 나올 때의 재시도/새니타이즈 로직은 서버 구현 시 결정
3. **가격·전환율 목표**: `수익화-기능기획.md` 오픈 이슈 1·2번과 동일, 이 문서로 해소되지 않음 — 그대로 유지
